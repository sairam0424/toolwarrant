# Changelog

Every change an operator can see is recorded here, one line of prose per
change, naming the test that proves it (a change to a document alone names
the document). The file follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
A pull request adds its line under Unreleased; the release commit moves those
lines under a `## [x.y.z] - YYYY-MM-DD` heading and leaves an empty
`## [Unreleased]` above them (CONTRIBUTING.md, Before you open a pull request;
docs/operations.md, Releasing). `make release-check` refuses a tree without
the Unreleased heading and, run as `make release-check VERSION=x.y.z`, one
whose changelog has no heading for that version.

## [Unreleased]

### Added

- `toolwarrant diff` prints `drift: GRADE (kinds)` after the `to:` header: the change from the from version to the to version classified by the new `internal/drift` package (CRITICAL for a parameter removed, retyped or newly required, an annotation hint loosened or the name changed; WARNING for a description, optional parameter, schema, annotations or `_meta` change, the description grade being owner decision O-6; INFO for the title and icons), or `drift: not classified (nothing approved to compare with)` against the empty document; the classification is advice, the gate stays the digest (`TestDiffPrintsTheDriftClassification`, `TestCompare_DescriptionChangeIsWarningNotInfo`, `TestCompare_HostileKeysAreEscapedInPaths`).
- `toolwarrant show` adds a CHANGE column with each version's grade against the approved one and, under the table, one line grouping the other versions by what they change, the worst group first; `show --json` gives every version `"change": {"severity", "kinds"}`, `null` for the approved version and while nothing is approved (`TestShowGroupsVersionsByChangeKinds`).
- `toolwarrant approve` prints `change versus the approved version N: GRADE (kinds)` on stderr before the suspicious-character review and never refuses on it (`TestApprovePrintsTheClassificationAndNeverGatesOnIt`).
- `toolwarrant export --sign-key PATH` signs the complete `MANIFEST.json` with the Ed25519 private key in that file (a PKCS#8 PEM; a regular file with mode 0600 or stricter, never a symbolic link; read from that path only, never from the environment or a flag value, and never printed) into `MANIFEST.json.sig` (the base64 signature over the exact bytes of the manifest) and writes the public key beside it as `MANIFEST.json.pub` (PKIX PEM); a key other users can read, a symbolic link, a directory, a file that is not one PKCS#8 `PRIVATE KEY` block or a key of another algorithm is refused with exit 1 before the catalog is opened, and `--commit` stages the two files and refuses a signature that does not sign the current manifest (decision D21 (e); `TestExportSignsTheManifestAndVerifyRoundTrips`, `TestExportRefusesAnUnsafeSigningKeyBeforeTouchingAnything`, `TestReadSigningKey_RefusesEveryUnsafeShape`, `TestWrite_SignsTheManifestAndASecondWriteTouchesNothing`, `TestWrite_WithoutAKeyLeavesTheSignatureFilesAloneAndVerifyRefusesThem`, `TestCommit_StagesTheSignatureFilesAndRefusesAStalePair`).
- `toolwarrant export verify --dir DIR --pub-key FILE [--expect-head HEX]` checks a signed export with the public key the operator holds and opens no database: `MANIFEST.json.pub` must record that key, `MANIFEST.json.sig` must be its signature over the exact bytes of `MANIFEST.json`, every listed file's bytes must hash to its digest, the entries on disk must be exactly the listed files, their server directories, the manifest and its two signature files (an extra, missing, renamed or nested entry, a symlink and a pending manifest each fail; the `.git` directory `--commit` keeps is skipped), and with `--expect-head` the manifest must record that audit head; the public key file is read under the same 8 KiB bound the export applies to a PEM key file, so an oversized file is refused before it is parsed; exit 1 names what was found (`TestExportSignsTheManifestAndVerifyRoundTrips`, `TestExportVerifyUsageHelpAndRefusals`, `TestVerify_RoundTripsASignedExport`, `TestVerify_FailsClosedOnEveryTamper`, `TestVerify_ReadsAVersionTwoManifestWithoutAHead`).
- `toolwarrant serve --max-crawl-age DURATION` bounds how long the latest complete crawl's word carries a `tools/call` on its own: with it set, a call whose only allowing evidence is a crawl older than the age is denied `crawl evidence too old` until a listing shows the approved definition or a crawl completes, so known limit L1 is bounded when the crawler stops; 0, the default, keeps the rule of every version before; the stats line gains the `stale` counter of those denials, `calls allowed=N denied=N (stale=N)`, and a negative value is a usage error (owner decision O-7, D21; `TestJudgeCall_StaleCrawlDeniesUnlessFreshlyListed`, `TestCheckRequest_MaxCrawlAgeZeroKeepsTheOldRule`, `TestCheckRequest_StaleCrawlCountsInStats`, `TestServeRejectsANegativeMaxCrawlAge`, `TestWriteStatsPinsTheLine`; end-to-end scenario R, `R_StaleCrawlDeniesCalls` of `TestEndToEnd`, right after I).

### Changed

- `MANIFEST.json` is version 3: between the status and the tool list it records `audit_head`, the head of the audit chain the catalog had verified when the approvals were read, in the same read transaction as them, so a crawl or a decision committed while the export runs lands in both the head and the files or in neither (the new `Store.ApprovedWithHead`; `Store.AuditHead` returns the head alone; the genesis for an empty log), and `digest_profile` (`full-v1`), and `export` prints both; an export after the log grew therefore rewrites the manifest (and its signature) with no tool file touched, and a version 2 manifest from an earlier release is still read as the record of the files to clean up (`TestWrite_ManifestRecordsTheAuditHeadAndProfile`, `TestParseManifest_ReadsVersionTwoAndThreeInTheirOwnShapes`, `TestWrite_CleansUpAfterAVersionTwoManifest`, `TestAuditHead_IsTheVerifiedHeadAndMovesWithTheLog`, `TestApprovedWithHead_HeadAndToolsComeFromOneSnapshot`).
- `toolwarrant serve --max-evidence-age` ages only listing evidence that agrees with the approval: a contradiction (another digest, or the conflict marker a bad page leaves) denies for as long as it stands and is released only by a clean listing, where before it stopped denying once older than the age (known limit L15, now closed; owner decision O-7, D21; `TestEvidence_ContradictionsNeverExpire`, `TestEvidence_ObservedDigestsExpire`, `TestJudgeCall_RuleTable`).
- The snapshot the processor serves from and `list` hand out approved digests anchored to the verified audit chain and no longer read or hash the stored definitions, and the ten-minute memory of verified rows is gone: every path that hands out bytes (`export`, `emit`, `show`, `diff`, every decision) hashes them on every call, so a rewritten definition is refused at once instead of after the memory lapsed, while a rewrite of the bytes alone, with the digest column intact, is no longer reported by the snapshot or by `list` (it cannot change what the gateway serves, and `export`, `emit`, `show`, `diff`, the decisions and `audit verify` refuse or name it); a reload of a 10000-tool server reads no definition bytes and hashes one or two small audit entries per tool (owner decision O-8, decision D21 (d); `TestSnapshot_ReadsNoCanonicalBytesAndStillServesTheAnchoredDigest`, `TestApproved_TamperedBytesAreCaughtAtOnce`, `TestVersions_TamperedBytesAreCaughtAtOnce`, `TestSnapshot_AChangedDigestColumnIsCaughtByTheAnchor`, `TestSnapshot_AnchorsTheDigestAndApprovedCatchesTamperedBytes`, `TestBenchmarkSnapshotHashesOnlyAuditEntries`).

## [0.2.0] - 2026-10-14

### Added

- `toolwarrant version` prints the module version Go embeds when the binary was built with `go install github.com/sairam0424/toolwarrant/cmd/toolwarrant@vX.Y.Z`, instead of `dev`; release archives are unchanged (`TestVersionFallsBackToTheModuleVersion`).
- The canary (`toolwarrant verify-gateway --admin HOST:PORT`) reads a processor's `policies.backendTLS` block (cert, key, root, hostname) from the emitted file and from the running gateway's `GET /api/config` and compares the two by presence and then field by field, so a processor link that carries TLS on one side only, or another root or hostname, is a `LIVE-CONFIG-MISMATCH` that names the field instead of one "field policies: not in the emitted file" line; a file without the block compares exactly as before (`TestEmittedConfigReadsTheProcessorTLS`, `TestLiveComparisonComparesTheProcessorTLS`, `TestLiveComparisonReportsAnInsecureTLSFlag`, `TestCompareProcessorsSeesAMissingBackendTLS`).
- `scripts/requalify-gateway.sh vX.Y.Z SHA256 [--e2e]` runs the checklist for moving the agentgateway pin (known limit L7) and the `ci` workflow gains a dispatch-only `requalify` job that runs it against a candidate release; docs/operations.md describes the procedure (`TestRequalifyScript_citesExistingTestsAndScenarios`, `TestRequalifyScript_reportsEveryItemOnce`, `TestRequalifyCI_dispatchJobRunsTheScript`).
- End-to-end scenario L compares the key paths agentgateway v1.6.0 drops, keeps and adds before the ExtMCP hook with the lists recorded in `e2e/testdata/gateway_tool_keys.json`, and every run writes the lists it saw to `logs/gateway_tool_keys.observed.json` in its work directory so that a moved pin is re-recorded by copying that file; the threat model (L2, L9), docs/decisions.md D10 and docs/operations.md state the recorded lists (`TestToolKeysGoldenRefusesWhatItCannotCompare`).
- `toolwarrant serve --tls-cert PATH --tls-key PATH [--tls-client-ca PATH]` terminates TLS 1.3 on the processor listener and, with a client CA, requires and verifies the gateway's client certificate; a verified client certificate satisfies the non-loopback listen rule in place of the shared secret (owner decision O-2; `TestServe_TLSWithClientCARequiresAClientCertificate`, `TestServeTLSRefusesAGroupReadableKey`).
- `toolwarrant emit --processor-tls NAME=cert=PATH,key=PATH,root=PATH,hostname=NAME` writes the gateway's `backendTLS` block on that server's processor entry, so that agentgateway v1.6.0 dials the processor with TLS and the client certificate at `cert` (end-to-end scenario Q drives the handshake); all four fields are required, the paths must be absolute paths on the gateway host, the hostname must be the DNS name of the processor's certificate, nothing of the block is recorded in the catalog (give the flag on every emit, as `--secret-env`), the printed `serve` command carries placeholders for `--tls-cert`, `--tls-key` and `--tls-client-ca`, and because the gateway's `--validate-only` opens the three files, `emit --gateway-binary` needs them on the emitting host (decision D19; `TestEmitWritesBackendTLSForAProcessorOverride`, `TestEmitWithTheGatewayBinaryNeedsTheTLSFilesOnThisHost`, `TestProcessorTLSIsWrittenUnderPolicies`, `TestGatewayValidateOnlyOpensBackendTLSFiles`).
- End-to-end scenario Q (`Q_ProcessorTLS` of `TestEndToEnd`, right after H) drives TLS on the processor link against the real agentgateway v1.6.0: a processor started with `serve --tls-cert`, `--tls-key` and `--tls-client-ca` behind an entry from `emit --processor-tls` lists and calls through the link (the gateway's client offers the h2 ALPN grpc-go requires, so no `alpn` field is written); a plaintext entry, a plaintext processor, a client certificate from another authority and a root bundle of garbage each fail closed; `verify-gateway --admin` is healthy on the TLS entry, `GET /api/config` renders the block as the four emitted values without key material, and a posted `insecure: true` makes the route serve under a root bundle of garbage it had just failed closed with (the gateway skips the verification of the processor's certificate) and is `LIVE-CONFIG-MISMATCH` naming the field; item 15 of `scripts/requalify-gateway.sh` reads the TLS tests and scenario Q instead of reporting `PENDING` (`TestRequalifyScript_reportsEveryItemOnce`); docs/decisions.md D19 quotes the log lines.
- Both `ci` test jobs run `go test` through gotestsum v1.13.0 and write every test slower than one second to the step summary; `make test-timings` prints the same table locally. A test may consult `testing.Short()` only when its full run exceeds thirty seconds on the runner per that table, and `TestShortPolicy_everyShortSkipIsNamedInCLAUDEAndRunsInFull` fails when such a test is not named in CLAUDE.md or its package is not run in full by the `test-full` job.
- `toolwarrant verify-gateway --expect-unhooked` turns the pinned gateway's forwarding of an id-less `tools/call` (HTTP 202, known limit L17) into a `KNOWN-LIMIT` line with exit 0, and any other answer to the probe into the failing verdict `PROBE-CHANGED`, so the probe detects a changed gateway instead of being skipped; SECURITY.md, the threat model, the README and docs/operations.md state the deployment requirement that only id-sending clients reach the gateway (decision D18; `TestExpectUnhookedTurnsThe202IntoAKnownLimitLine`, `TestExpectUnhookedFailsWhenTheGatewayStopsForwarding`, `TestExpectUnhookedAndNoProbeAreExclusive`).

### Changed

- `make release-check`, and with it the `ci` release-check job on every pull request, refuses a `go.mod` that carries a `replace` or `exclude` directive or that cannot be read (a `retract` is allowed), a `CHANGELOG.md` without its `## [Unreleased]` heading and, run as `make release-check VERSION=x.y.z`, a changelog without the `## [x.y.z] - YYYY-MM-DD` heading for the version being released (`TestReleaseGuards_refuseAReplaceOrExcludeDirectiveInGoMod`, `TestReleaseGuards_refuseAChangelogWithoutAnUnreleasedSection`, `TestReleaseGuards_refuseAVersionWithoutADatedChangelogEntry`).
- The `ci` docs job checks that every test name `CHANGELOG.md` and CONTRIBUTING.md cite is a test function and that their relative links resolve, as it already did for README.md, SECURITY.md, CLAUDE.md, `docs/` and `seam/RESULTS.md`; CONTRIBUTING.md states the changelog rule and names the two tests that prove the changelog guards.
- SECURITY.md promises an acknowledgement of a vulnerability report within two days, and a confirmed problem still open fourteen days after the report gets a dated note in the advisory saying why and when (owner decision O-4; the policy said seven days before).
- A tag is never moved or deleted; a bad release is a new tag plus a `retract vX.Y.Z // reason` directive in `go.mod` (SECURITY.md Release integrity, CONTRIBUTING.md Branches and commits, docs/operations.md Releasing). Release candidates and their releases are kept rather than deleted before the final tag.
- SECURITY.md names the two public logs that anchor a release, the Rekor entry inside the signature bundle and sum.golang.org's record of the module at each tag, and gives the procedure that rebuilds a release byte for byte from a clean clone at the tag; docs/operations.md Releasing fetches each new tag through the module proxy right after publishing, checks that the record exists, and records the repository settings as they stand (rulesets, secret scanning, immutable releases still to be enabled).
- The `release` workflow takes a tag's notes from this file through `scripts/release-notes.sh` (a final tag its own section; a candidate the version's section once the release commit has added it, else Unreleased; a missing heading or an empty section stops the run before any draft exists) instead of the commit list grouped by type, attests the four archives and four SBOMs with SLSA build provenance and attaches the bundle to the release as `toolwarrant_<version>_provenance.intoto.jsonl` (`gh attestation verify`), rebuilds linux/amd64 with the command SECURITY.md documents and compares it with the archive, and refuses a tag whose release is already published; SECURITY.md supports 0.2.x, puts the gh verification path first and keeps the cosign path, and docs/decisions.md records the round as D20 (`TestReleaseNotes_aFinalTagTakesItsOwnSectionAndStopsAtTheLinks`, `TestReleaseNotes_aCandidateTakesUnreleasedUntilTheReleaseCommit`, `TestReleaseNotes_refuseAnEmptySectionOrAMissingHeading`, `TestReleaseNotes_refuseATagThatIsNotAVersion`, `TestReleaseNotes_everyReleasedVersionInTheTreeHasNotes`, `TestReleaseNotes_theWorkflowHandsTheFileToGoreleaserAndKeepsThePipe`).

### Fixed

- The catalog pins `synchronous(FULL)` in the connection string of every pooled connection of every open mode, so an approval, a rollback or a crawl is on the disk before its command returns, across a power loss and not only across a crash of the process; the driver's compile-time default was relied on before (`TestOpen_EveryPooledConnectionIsSynchronousFullWithForeignKeysInWAL`).
- The canary's quoted count of the configuration fields agentgateway v1.6.0 declares is 36, not 37.

## [0.1.1] - 2026-10-14

### Fixed

- `Approved`, which `emit` and `export` read, anchors the state of every tool row of the server before leaving one out, so a tool whose state column was edited by hand is `ErrCorrupt` on the emit path as it already was for `list`, `audit verify` and the crawl; before, `emit` wrote a gateway file with one allow rule fewer, exit 0 and no change line (`TestApproved_ToolHiddenByAColumnFlipIsCorrupt`, `TestEmitRefusesACatalogWhoseToolStateColumnWasEdited`).
- `Snapshot`, which the processor serves from, anchors every row of the server before leaving deprecated ones out, so a row flipped to deprecated by hand is `ErrCorrupt` on the serving path instead of a tool that vanishes from the policy without an error (`TestSnapshot_ToolDeprecatedByAColumnFlipIsCorrupt`).

### Changed

- `make release-check`, which the `ci` release-check job runs on every pull request, fails when the platform list of `scripts/gen-third-party-notices.sh` differs from the goos x goarch of `.goreleaser.yaml`, since the notices would then miss a platform's modules, and when the signing block loses `--bundle`, the flag without which cosign v3 writes no signature.
- The `ci` lint job runs actionlint v1.7.12 on both workflow files, so an expression or schema error in `release.yml` fails a pull request instead of the tag that runs it, which is how three release candidates were spent on 2026-10-12.

## [0.1.0] - 2026-10-12

First release. toolwarrant for MCP is a control plane in front of agentgateway v1.6.0: it crawls upstream MCP servers, stores every tool definition as an immutable version identified by the SHA-256 of its RFC 8785 canonical JSON, lets a named person approve one exact digest, emits the gateway configuration and enforces the approval at the gateway as an ExtMCP processor in strict mode, so that a tool is served only while its live definition hashes to the approved digest. Nothing is served until approved and a crawl never approves anything. The catalog is an SQLite file at schema v6 with a hash-chained audit log. The release carries the `toolwarrant` binary for darwin/arm64, darwin/amd64, linux/amd64 and linux/arm64, built from the tagged commit with CGO disabled and `-trimpath`, one SPDX SBOM beside each archive, and a checksums file signed keyless with cosign by the release workflow (docs/decisions.md D16; verification in SECURITY.md, Release integrity).
