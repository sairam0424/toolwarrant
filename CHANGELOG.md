# Changelog

Every change an operator can see is recorded here, one line of prose per
change, naming the test that proves it (a change to a document alone names
the document). The file follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
and the versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
A pull request adds its line under Unreleased; the release commit moves those
lines under a `## [x.y.z] - YYYY-MM-DD` heading and leaves an empty
`## [Unreleased]` above them (CONTRIBUTING.md, Before you open a pull request;
docs/operations.md, Releasing). `make release-check` refuses a tree without
the Unreleased heading and, run as `make release-check VERSION=x.y.z`, one
whose changelog has no heading for that version.

## [Unreleased]

### Changed

- `toolwarrant version` prints a third line, `commit` and the first twelve characters of the revision the go command stamped into the binary, `+dirty` appended when the checkout had uncommitted changes, and `commit unknown` when the build carries no version-control stamp (a `go install` of the module from the proxy, `go run`, `go test`); a release archive's binary names the tagged commit, which `go version -m` showed in full and the command did not, and the release binaries up to v0.4.0 predate the line (`TestBuildCommit_NamesTheRevisionTheToolchainStamped`, `TestHelpAndVersion`, `TestVersionFallsBackToTheModuleVersion`).
- `trust add` and `trust remove` run as the system actor (`--as crawler`, or `TOOLWARRANT_ACTOR` naming it) are refused with `the system actor cannot change the trust list; pass --as with your own name`, exit 2, in place of the decision sentence that named approve, reject and the other decisions, as `trust init` already was (`TestTrustUsageHelpAndRefusals`).

### Fixed

- `audit verify`'s line about the approvals made before the trust bootstrap names the three signed steps that sign one, `unsigned approvals in service: N (approved before the cut-over at entry B; to sign one, disable, enable and approve it, each signed): server/tool, ...`, in place of `re-approve them to sign them`, which read as one step while a signed `approve` of a tool whose approval is in force is refused with `cannot approve in state enabled`, and joins the tools with a comma and a space, as docs/operations.md shows them, in place of a bare comma (`TestAuditVerifyReportsTheSignedRecordsAndLegacyApprovals`); docs/threat-model.md (L13) and docs/decisions.md (D22, decision (6)) carry the same three-step advice in place of the one-step `re-approve`.
- `trust init` run as the system actor (`--as crawler`, or `TOOLWARRANT_ACTOR` naming it) is refused with `the system actor cannot start the trust list; pass --as with your own name`, exit 2, in place of the decision sentence that named approve, reject and the other decisions and not the command that was refused (`TestTrustInitRefusesASecondBootstrapAndTheSystemActor`).
- docs/operations.md, Verifying a decision with stock OpenSSH: the recipe takes one `audit list --json` listing and selects the whole newest `decision.signed` record with jq's `last(...)` (or one entry with `select(.seq == N)`) instead of piping the field through `tail -1`, which kept only the last line of the eight-line armored `-----BEGIN SSH SIGNATURE-----` block and made `ssh-keygen -Y verify` fail with `Couldn't parse signature: missing header`; the fixed recipe, run on 2026-10-16 against a catalog this build wrote, printed `Good "decision@toolwarrant.invalid" signature for alice with ED25519 key SHA256:...`.
- docs/operations.md, the schema v7 migration procedure: every open, the read-only and forensic ones included, creates the SQLite `-wal` and `-shm` sidecars beside the database when they are missing, a copy of the `.db` alone is a complete backup only while the `-wal` is empty (stop the processors and every other process first), and `emit` writes a `server.processor_set` audit entry for every processor address it records, so the heads are compared right after `init` and before `emit`.
- SECURITY.md, Release integrity, and docs/operations.md, Releasing: the reproducible rebuild needs a clean `git clone` checked out at the tag, not a `git archive` export or a source tarball, since the binaries embed `vcs.revision`, `vcs.time`, `vcs.modified` and the module version, which the go command reads from `.git`.

## [0.4.0] - 2026-10-16

This release writes catalog schema v7. A catalog from an earlier build is migrated in place when it is schema v6 (v0.1.0 to v0.3.x) and refused otherwise: stop the processors, back the file up and record its audit head with the build that wrote it, then run `init` with this build (it adds one table and its guards and rewrites nothing, so the head is unchanged) and start the processors. Every command but `serve`, `audit verify` and `audit list` migrates the file the same way, `list` and `show` included, so take the backup before running any of them with this build; a v0.3.x build refuses the migrated file. Once `trust init` has run, every human decision must be signed by a key the trust list names (D22).

### Changed

- New internal package `internal/trust`, the rules of the signed operator trust list of v0.4 (D22 (c)), with no command change yet: a list is valid when its names are D7 names after normalisation and unique, its keys canonical, within the key policy and unique by fingerprint, one to 64 operators and the threshold exactly 1 (owner decision O-14); the first list is version 1 signed by one of its own keys, and by the pinned root when one is given; every later list is exactly one version above the list in force and signed by a key of both lists, so version N and version N+2 are refused as rollback and the last signer cannot remove itself (`TestCheckRotation_MustBeExactlyNextVersionAndSignedByAKeyOfBothLists`); authorisation is separate from signature validity, a valid signature from a key the list does not name authorises nothing; the `allowed_signers` rendering verifies with stock `ssh-keygen -Y verify`; the catalog applies these rules to its chain in a later pull request.
- `go.mod` adds `github.com/hiddeco/sshsig` v0.2.0 and `golang.org/x/crypto` v0.58.0, whose own module graph moves `golang.org/x/text` to v0.43.0, `golang.org/x/sys` to v0.49.0 and `golang.org/x/sync` to v0.24.0, and `THIRD_PARTY_NOTICES.md` is regenerated with them (section 1 gains the two modules, their `Linked into` column reading `none yet` until a command imports `internal/signing`, and its heading and paragraph now say that a row names the binaries that link the module; section 3 gains `golang.org/x/term`); they back the new `internal/signing` package, the OpenSSH `sshsig` records behind the signed decisions of v0.4, whose signatures stock `ssh-keygen -Y verify` accepts and whose verifier accepts what `ssh-keygen -Y sign` writes, through a key file or through ssh-agent (`TestOpenSSH_SignatureVerifiesWithSshKeygenAndTheReverse`); no command changes yet.

- `toolwarrant export verify --dir DIR --pub-key FILE [--expect-head HEX]` checks a signed export with the public key the operator holds and opens no database: `MANIFEST.json.pub` must record that key, `MANIFEST.json.sig` must be its signature over the exact bytes of `MANIFEST.json`, every listed file's bytes must hash to its digest, the entries on disk must be exactly the listed files, their server directories, the manifest and its two signature files (an extra, missing, renamed or nested entry, a symlink and a pending manifest each fail; the `.git` directory `--commit` keeps is skipped), and with `--expect-head` the manifest must record that audit head; the public key file is read under the same 8 KiB bound the export applies to a PEM key file, so an oversized file is refused before it is parsed; exit 1 names what was found (`TestExportSignsTheManifestAndVerifyRoundTrips`, `TestExportVerifyUsageHelpAndRefusals`, `TestVerify_RoundTripsASignedExport`, `TestVerify_FailsClosedOnEveryTamper`, `TestVerify_ReadsAVersionTwoManifestWithoutAHead`).

## [0.1.0] - 2026-10-12

First release. toolwarrant for MCP is a control plane in front of agentgateway v1.6.0: it crawls upstream MCP servers, stores every tool definition as an immutable version identified by the SHA-256 of its RFC 8785 canonical JSON, lets a named person approve one exact digest, emits the gateway configuration and enforces the approval at the gateway as an ExtMCP processor in strict mode, so that a tool is served only while its live definition hashes to the approved digest. Nothing is served until approved and a crawl never approves anything. The catalog is an SQLite file at schema v6 with a hash-chained audit log. The release carries the `toolwarrant` binary for darwin/arm64, darwin/amd64, linux/amd64 and linux/arm64, built from the tagged commit with CGO disabled and `-trimpath`, one SPDX SBOM beside each archive, and a checksums file signed keyless with cosign by the release workflow (docs/decisions.md D16; verification in SECURITY.md, Release integrity).
