# Threat model

This document adapts the ranked threat model of the design report (section 6.1,
written before any code existed) to what toolwarrant v0.1 actually is: a Go
control plane and ExtMCP processor over SQLite, in front of agentgateway v1.6.0,
with native MCP upstreams only, no LLM path, no OpenAPI or gRPC ingestion and no
redaction. Threats that exist only in the fuller design (description generation,
`$ref` dereferencing, gRPC reflection, response redaction) are not listed; they
are non-goals of v0.1 and the code has no surface for them.

Every control in the first table is traceable to a test in this repository or to
a numbered result in [../seam/RESULTS.md](../seam/RESULTS.md). Tests are cited
as the package name followed by the test function names; the packages live under
`internal/` except `cmd`, which is `cmd/toolwarrant`. Where a control is complete in a package but
its CLI wiring belongs to the wave in progress, the row says "CLI wiring: to be
verified by the end-to-end test".

Status of the CLI tests at commit 49873a7: four `cmd/toolwarrant` tests fail
because they encode behaviour that decisions D2, D3 and D4 changed or need
wiring the current wave adds (`TestServeEnforcesApprovalsOverGRPC`,
`TestApprovalFlowWithDriftRejectEnableAndRollback`,
`TestCrawlRefusesInvisibleCharactersInToolNames`,
`TestAuditVerifyDetectsATamperedDatabase`). They are cited below only where an
internal-package test proves the same control.

## Actors and trust boundaries

- The upstream MCP server is hostile. Everything it sends, including tool names,
  is attacker-controlled input to the crawler, the processor, the diff renderer,
  the exporter and every terminal an operator reads.
- The agentgateway binary and its configuration file are trusted to run the
  processor chain the file names; the file itself is a defended artefact (its
  header carries a hash) because whoever edits it can drop the guard.
- The processor is part of the gateway's trusted computing base: its answer
  decides what is served. Whoever can reach its listener without the shared
  secret decides too.
- The catalog file is trusted only after its own checks: every approval handed
  out is re-hashed, guard objects must be present, and the audit chain must
  verify.
- Operators are named but not authenticated beyond the OS: `--as NAME` and
  `TOOLWARRANT_ACTOR` are honoured as given, after normalisation. Single tenant.

## Residual risks and what an operator can do

| # | Residual risk | Why it remains | What an operator can do |
| --- | --- | --- | --- |
| L1 | A client that never re-lists can call a tool that changed upstream until the processor's evidence is refreshed by a gateway listing or a crawl | The `tools/call` hook carries no definition (RESULTS.md F1, test 4). The processor can only compare evidence it has | Crawl often (`crawl SERVER --every 1m`, minimum 1 s); the gap is bounded by the crawl cadence. Set `serve --max-evidence-age` so stale listing evidence expires. Prefer clients that re-list before calling |
| L2 | A tool whose definition carries a top-level or `annotations` key agentgateway v1.6.0 does not know can never be served: the gateway re-serialises it before the hook and drops the key, so its digest never matches | Decision D10: v0.1 does not hash a projection of what the gateway re-serialises; it reports the mismatch (`Stats.ToolsMismatched`, MISMATCH in `verify-gateway`, to be verified by the end-to-end test) | Ask the upstream to drop the key, or wait for a gateway release that preserves it. Watch the mismatch counter; a mismatch on a tool you just approved is this case, not drift |
| L3 | A reload that removes the processor from a route unguards new sessions only; existing sessions keep the guard, so processor statistics cannot reveal the removal | The gateway binds the processor chain per MCP session (RESULTS.md test 14 as corrected) | Run `verify-gateway --every` as a canary; it opens a new session every run. Keep one owner for the configuration file and never edit it by hand; `--config FILE` reports CONFIG-EDITED (to be verified by the end-to-end test) |
| L4 | An upstream can tell the crawler apart from the gateway and serve each a different definition | Request shape, timing and source address identify a crawler whatever clientInfo says | Rely on the processor's live check, which hashes what the gateway was actually served; the crawl is for people, the processor is the guard. Crawl from the same network path as the gateway where you can |
| L5 | Definitions with numbers that are not exact doubles cannot be approved or served | D1 refuses them so that two values cannot share a digest | Ask the upstream to express such numbers as strings or within double precision. The crawl reports the tool as unusable with reason `not-canonical` |
| L6 | A tool that gains more than 20 new digests between decisions is hidden until someone decides | The proposal budget stops a hostile upstream from growing the database | Decide (approve, reject or roll back) to reset the budget; if a legitimate upstream changes that fast, it is not a tool whose definition can be pinned |
| L7 | agentgateway v1.6.0 only; other releases are unqualified | Breaking changes about every five weeks, unversioned schema, young ExtMCP protocol | Pin the gateway binary by checksum; re-run the emitter's binary validation tests and the end-to-end test before moving |
| L8 | Single tenant, single SQLite file, no high availability | Scope of v0.1 | Back up the database file and its audit head together; run one processor per upstream on the gateway host |
| L9 | Any `_meta` change is drift | D1: hosts act on `_meta`, so it is part of the digest | A tool with a volatile `_meta` member cannot stay approved; ask the upstream to keep `_meta` stable |
| L10 | The gateway's route bind listens on every interface | The v1.6.0 schema has no bind address under `binds[]` | Firewall the listen port; run the gateway in a private network. Admin, stats and readiness listeners are already on 127.0.0.1 |
| L11 | Processor transport is plain `host:port`; no TLS between gateway and processor | The schema documents only host:port for `processors[].host`; `backendTLS` is a later step | Keep the processor on loopback or a unix socket on the gateway host and use the shared secret |
| L12 | The end-to-end added latency has not been re-measured since the digest, filter and cache changes | The RESULTS.md table was measured with the spike's processor | Measure with `toolwarrant serve` on pages of realistic size before relying on the 50 ms budget; the digest cache keeps an unchanged 100-tool page at about 3 to 4 ms per hook in benchmarks on a loaded machine |
| L13 | Operators are not authenticated: `--as` and `TOOLWARRANT_ACTOR` are taken as given | Single-tenant v0.1; identity comes from the OS | Run the CLI under per-person OS accounts; keep the database 0600 so only those accounts can decide; export to git for a second record of who approved what |
| L14 | Homoglyphs (a Cyrillic letter that looks Latin) pass the diff renderer unflagged; behaviour change behind an unchanged definition is invisible to a digest | Documented limits of `internal/textdiff` and of definition hashing in general | Read names and descriptions with that in mind; pair the gate with least-privilege upstream credentials |
| L15 | `MaxEvidenceAge` also ages conflict markers, so a contradiction older than the age stops denying until the next listing re-records it | Trade-off between stale evidence and stale denials | Leave it at 0 (never expires) unless stale listing evidence is a real problem; keep crawling |
| L16 | A reload of a 10000-tool server costs up to about 2.5 GB of hashing because the snapshot re-checks every approved definition | Every read path re-hashes what it hands out; the processor reloads only when the catalog generation moves | Keep approvals per server in the hundreds or low thousands; split very large upstreams |
