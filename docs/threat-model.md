# Threat model

This document adapts the ranked threat model of the design report (section 6.1,
written before any code existed) to what toolwarrant v0.1 actually is: a Go
control plane and ExtMCP processor over SQLite, in front of agentgateway v1.6.0,
with native MCP upstreams only, no LLM path, no OpenAPI or gRPC ingestion and no
redaction. Threats that exist only in the fuller design (description generation,
`$ref` dereferencing, gRPC reflection, response redaction) are not listed; they
are non-goals of v0.1 and the code has no surface for them.

Every control in the first table is traceable to a test in this repository or to
a numbered result in [../seam/RESULTS.md](../seam/RESULTS.md). Tests are cited
as the package name followed by the test function names; the packages live under
`internal/` except `cmd`, which is `cmd/toolwarrant`, and `e2e`, whose
`TestEndToEnd` runs the whole chain on the real agentgateway v1.6.0 binary
(scenarios A to P; `make e2e`; `demo/run.sh` keeps the last run in
`demo/last-run.log`). Where a control depends on the live gateway, the scenario
letter is the proof. The `docs` job of
[../.github/workflows/ci.yml](../.github/workflows/ci.yml) checks that every
test name cited in the documents exists in the tree, so a renamed test cannot
orphan a documented control. Two observations of the second review (rows 25 and
26) were made on the real gateway but are not yet pinned by a test here; the
rows say so.

## Actors and trust boundaries

- The upstream MCP server is hostile. Everything it sends, including tool names,
  is attacker-controlled input to the crawler, the processor, the diff renderer,
  the exporter and every terminal an operator reads.
- The agentgateway binary and its configuration file are trusted to run the
  processor chain the file names. The file's header carries an unkeyed SHA-256
  of its body: tamper-evidence against accidental edits and against edits that
  leave the header alone, not a proof of origin (limit L19). Whoever edits the
  file can drop the guard, so the file has one owner and the canary checks both
  the file and the gateway's live configuration.
- The processor is part of the gateway's trusted computing base: its answer
  decides what is served. Whoever can reach its listener without the shared
  secret decides too.
- The gateway's admin listener is part of the trusted computing base as well.
  The emitted file binds it, with the stats and readiness listeners, to
  127.0.0.1, but the admin API is unauthenticated: it hands out the loaded
  configuration, shared secret included (`GET /config_dump`), and accepts a
  replacement configuration (`POST /api/config`) that the gateway applies and
  writes back to the watched file. Every local user of the gateway host is
  therefore inside the boundary (limit L18). `emit --disable-admin` turns the
  admin API off, at the price of the canary's live-configuration comparison.
- The catalog file is trusted only after its own checks: every approval handed
  out is re-hashed and must have an approval record, guard objects must be
  present with the definition `init` wrote (checked at open and on every
  snapshot load), and the audit chain must verify. `Store.Integrity` in
  `internal/catalog` cross-checks the mutable registry against the approvals
  table and the audit log and lists every disagreement, and `audit verify` runs
  it after the chain check (`integrity ok` or `integrity problem` lines, exit
  code 1 on any problem).
- Operators are named but not authenticated beyond the OS: `--as NAME` and
  `TOOLWARRANT_ACTOR` are honoured as given, after normalisation. Single tenant.

## Residual risks and what an operator can do

| # | Residual risk | Why it remains | What an operator can do |
| --- | --- | --- | --- |
| L1 | A client that never re-lists can call a tool that changed upstream until the processor's evidence is refreshed by a gateway listing or a crawl | The `tools/call` hook carries no definition (RESULTS.md F1, test 4). The processor can only compare evidence it has. e2e scenario C measured both paths: denied 1.5 ms after another session listed the drifted definition, and otherwise as soon as the crawl recorded it. A page the processor denies as a whole leaves a conflict marker on every catalog tool it listed (third round), so a decoy cannot keep the older evidence alive | Crawl often (`crawl SERVER --every 1m`, minimum 1 s); the gap is bounded by the crawl cadence. Set `serve --max-evidence-age` so stale listing evidence expires. Prefer clients that re-list before calling |
| L2 | A tool whose definition carries a key agentgateway v1.6.0 does not preserve can never be served: the gateway re-serialises it before the hook and drops the key, so its digest never matches. e2e scenario L recorded the pinned binary dropping the unknown top-level key `x-vendor` (with `x-vendor.tier`) and `annotations.x-risk` while keeping `annotations.title`, `annotations.readOnlyHint` and the `_meta` member `vendor/ui`; the second review also saw a `_meta` member named `ui` and a top-level `execution` key dropped, so some `_meta` members survive and some do not | Decision D10: v0.1 does not hash a projection of what the gateway re-serialises; it reports the mismatch (`Stats.ToolsMismatched`, the `digest mismatch` log line) and hides the tool, so `verify-gateway` reports it as MISSING; MISMATCH appears only as the sub-label of a LEAK line when a route without its processor serves the re-serialised bytes | Ask the upstream to drop the key, or wait for a gateway release that preserves it. Watch the `mismatched` counter; a mismatch on a tool you just approved is this case, not drift |
| L3 | A reload that removes the processor from a route unguards new sessions only; existing sessions keep the guard, so processor statistics cannot reveal the removal | The gateway binds the processor chain per MCP session (RESULTS.md test 14 as corrected; reproduced by the second review) | Run `verify-gateway --every` as a canary; it opens a new session every run. Keep one owner for the configuration file and never edit it by hand; `--config FILE` reports CONFIG-EDITED and `--admin ADDR` reports LIVE-CONFIG-MISMATCH when the gateway runs something else |
| L4 | An upstream can tell the crawler apart from the gateway and serve each a different definition | Request shape, timing and source address identify a crawler whatever clientInfo says (the crawler's clientInfo is the library default, `mcp-client`; its User-Agent is Go's default) | Rely on the processor's live check, which hashes what the gateway was actually served; the crawl is for people, the processor is the guard. | L8 | Single tenant, single SQLite file, no high availability | Scope of v0.1 | Back up the database file and its audit head together; run one processor per upstream on the gateway host |
